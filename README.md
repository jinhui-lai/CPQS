# CPQS: Cardinality-Pivoted Query Synthesis

CPQS (Cardinality-Pivoted Query Synthesis) is an automated testing framework for **DBMS performance issues**. Instead of cross-query comparison or a complex differential oracle, it synthesizes SQL whose **expected access cardinalities can be derived independently**, then compares those bounds with the records actually examined at runtime via `EXPLAIN` / `EXPLAIN ANALYZE`. A large gap is treated as a potential performance bug.

The Python package name is `cpqs`. This repository contains the source code, dependency notes, and a summary of confirmed bug reports in [`bug.md`](bug.md).

Supported evaluation targets in this guide: **Oracle**, **MySQL**, **MariaDB**, **TiDB**, and **CockroachDB**.

---

## 1. Core idea

Traditional performance testing (cross-version or cross-engine comparison) relies on a relationship that should hold between two queries or two executions. If both sides are affected by the same defect, the relationship can still hold and the bug is missed. Keeping comparisons valid also tends to restrict which SQL features can appear in tests.

CPQS takes a different approach:

1. **Build the database itself.** All DDL and DML are generated by the tool: primary keys, unique indexes, non-unique ordered indexes, partitions, `CHECK` constraints, foreign keys, and controlled row distributions (multiplicity, null rate, partition occupancy) are known up front.
2. **Write queries around provable access paths.** Examples include unique equality / `IN`, ordered ranges, `ORDER BY … LIMIT`, partition pruning, and contradictory predicates (expected access 0). Every retained query has at least one base-relation occurrence (the cardinality pivot) with a **tight, independently justified** access upper bound \(C_{\mathrm{expected}}\).
3. **Compare records examined, not rows returned.** A selective predicate can return one row after either an index lookup or a full-table scan. CPQS tracks how many records scans and probes actually examine.
4. **Report only when the bound is sound.** Candidates whose preconditions fail or whose bound is too loose (e.g. \(U/N > 0.01\)) are discarded, so the tool never “guesses” cardinality for arbitrary SQL.

If the optimizer misses an available index, prune, or elimination strategy, actual access far exceeds the expected bound and CPQS can flag it.

## 2. Workflow

The pipeline has four stages from the paper. A **two-level multi-armed bandit** allocates the execution budget:

```
┌──────────────────────┐   ┌──────────────────────────┐   ┌─────────────────┐   ┌──────────────────────┐
│ 1. Database state    │ → │ 2. Cardinality-pivoted   │ → │ 3. Cardinality  │ → │ 4. Feedback-guided  │
│    generation        │   │    query synthesis       │   │    validation   │   │    exploration      │
│ DDL/DML + mutation   │   │ seed + bound-aware mut.  │   │ EXPLAIN/ANALYZE │   │ query / state level │
└──────────────────────┘   └──────────────────────────┘   └─────────────────┘   └──────────────────────┘
```

### 2.1 Access-path-oriented schema and data

- Dialect-specific tables, indexes, partitions, and constraints are created; unique keys and controllable multiplicities are inserted.
- When query-level exploration stalls, the state-level bandit changes index shapes, partition kinds, column types, row counts, null distribution, range density, or partition skew, then rederives bounds under the new state.

### 2.2 Cardinality-pivoted query synthesis

- **Seed:** pick a cardinality primitive justified by the current state (e.g. `c0 IN (…)` with expected access \(m\)) and build a minimal SQL AST around it.
- **Bound-aware mutation:** rewrite the AST or expressions while keeping (or re-proving) the pivot bound—joins, CTEs, derived tables, `DISTINCT` / `GROUP BY` / windows, `IN`↔`OR`, literal rewrites, `ORDER BY LIMIT`, and so on. Bound outcomes are preservation, tightening, composition, or invalidation; **invalidating mutations are rejected** instead of being given speculative bounds.

### 2.3 Cardinality validation

- After refreshing statistics, run `EXPLAIN` and, when needed, `EXPLAIN ANALYZE` (or a dialect equivalent).
- Compare plan **examination counts** (including `rows×loops` and similar) with \(C_{\mathrm{expected}}\). By default both the estimate and the actual count must exceed a large ratio threshold (e.g. about \(200\times\)) before a bug is recorded; an `ANALYZE` timeout after an overshooting estimate also counts as a bug.
- Joins and similar shapes may carry per-input bounds; the bandit reward still focuses on the pivot.

### 2.4 Feedback-guided exploration

- Reward \(u = \frac{2}{3}d + \frac{1}{3}g\): \(d\) measures the cardinality gap, \(g\) is 1 when the normalized plan signature is new.
- **Query level:** UCB selects mutation operators under the current database state; after \(K\) consecutive pulls with no larger \(d\) and no new plan, the episode stalls.
- **State level:** after a stall, mutate the database state and start a new query episode; the state arm receives the mean reward of that episode.

Mismatches are written as reproducible POCs under `pocs/<db>/bug-NNNN-<kind>.sql` (DDL, DML, query, plan excerpt, and expected cardinality).

## 3. Results (confirmed bugs)

On the five target DBMSs, CPQS found previously unknown performance issues that vendors confirmed. [`bug.md`](bug.md) lists reports and confirmation links. Rough counts by engine:

| DBMS | Confirmed items (see bug.md) | Typical shape |
| --- | --- | --- |
| Oracle | 2+ | Combined `MIN`/`MAX` falls back to a full scan; FULL OUTER + disjunction misses key ranges |
| MySQL | 8 | Missed unique lookup / ordered LIMIT / partition prune paths |
| MariaDB | 4 | Similar index and join access issues |
| TiDB | 4 | Inefficient ordered, partition, or join plans |
| CockroachDB | 4 | FULL OUTER + disjunction full PK scans; dual-aggregate cartesian products |

The paper evaluation also shows that, under the same 24-hour budget, CPQS finds more unique performance bugs than baselines such as APOLLO, AMOEBA, CERT, HULK, PUPPY, and SCor. Relative to a seed-only ablation (no mutations), the mutation + bandit version finds substantially more bugs.

See [`bug.md`](bug.md) for details and reproducing SQL.

## 4. Setup

### 4.1 Requirements

- Linux (including WSL2) or macOS
- Python 3.10+ (3.11 / 3.12 recommended)
- Docker (to run target DBMSs; this guide prefers `docker run` / `docker start`)
- At least 4–8 GiB free RAM recommended; Oracle first boot needs more time and memory

### 4.2 Install CPQS

```bash
cd /path/to/CPQS          # this directory (contains cpqs/ and requirements.txt)

python3 -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

`requirements.txt` includes:

- `pymysql` — MySQL / MariaDB / TiDB
- `psycopg[binary]` — CockroachDB
- `oracledb` — Oracle

Verify the install:

```bash
# Run from the repository root so the `cpqs` package is importable
PYTHONPATH=. python3 -m cpqs --help
```

To avoid typing `PYTHONPATH=.` every time:

```bash
export PYTHONPATH="$(pwd):${PYTHONPATH}"
# or append that line to .venv/bin/activate
```

Unless noted otherwise, the commands below assume the current directory is this repository root and `PYTHONPATH=.` is set (or prefixed on each command).

CPQS/

## 5. Starting database services

**Prefer one heavy DBMS at a time** (especially Oracle). Stop the container with `docker stop <name>` when finished to free memory.

### 5.1 `docker run` / `docker start` (recommended)

```bash
# MySQL 8.4 → 3306, empty root password
docker start mysql 2>/dev/null || \
  docker run -d --name mysql -p 3306:3306 \
    -e MYSQL_ALLOW_EMPTY_PASSWORD=yes mysql:8.4

# MariaDB 11.4 → host port 3307
docker start mariadb 2>/dev/null || \
  docker run -d --name mariadb -p 3307:3306 \
    -e MARIADB_ALLOW_EMPTY_ROOT_PASSWORD=yes mariadb:11.4

# CockroachDB → 26257 (container name often roach1)
docker start roach1 2>/dev/null || \
  docker run -d --name roach1 -p 26257:26257 -p 8080:8080 \
    cockroachdb/cockroach:v24.3.0 start-single-node --insecure

# TiDB → 4000 (single-node unistore, good for testing)
docker rm -f tidb 2>/dev/null
docker run -d --name tidb -p 4000:4000 \
  pingcap/tidb:v8.5.0 --store=unistore --path=/tmp/tidb

# Oracle Free 23 → 1521 (first boot can take several minutes)
# ORACLE_PASSWORD is the SYSTEM password; keep it in sync with --password below
docker start oracle23 2>/dev/null || \
  docker run -d --name oracle23 -p 1521:1521 \
    -e ORACLE_PASSWORD=oracle gvenzl/oracle-free:23.5-slim
```

Wait until ready:

```bash
# MySQL / MariaDB / TiDB
docker exec mysql mysqladmin ping -uroot --silent && echo ready

# Cockroach
docker exec roach1 ./cockroach sql --insecure -e 'SELECT 1'

# Oracle: connect only after STATUS is healthy
docker ps --filter name=oracle23
```

Stop when done:

```bash
docker stop mysql mariadb roach1 tidb oracle23
```

### 5.2 Docker Compose (optional)

If the Compose plugin is available:

docker compose up -d mysql          # start one service

## 6. Testing a DBMS with CPQS

### 6.1 Minimal smoke run (verify the path)

```bash
export PYTHONPATH=.

# Generate SQL only; no live DBMS
python3 -m cpqs --db mysql --dry-run --queries 20

# Live MySQL, small budget (still keep --rows at least 10000)
python3 -m cpqs --db mysql --port 3306 --user root --password '' \
  --rows 10000 --tables 3 \
  --queries 50 --queries-per-state 50 --stale-queries 20 --max-states 2 \
  --overestimate-factor 200 --seed 1
```

A successful run prints lines such as `=== state … ===`, `ok …`, occasionally `BUG #n … -> pocs/mysql/...`, and ends with:

```text
done generated=… explained=… skipped=… bugs=… states=…
```

- Exit code `0`: no new bug recorded this run  
- Exit code `2`: at least one POC was written  

### 6.2 Longer runs (recommended settings)

Goal: cover query mutations and state mutations within a controllable budget.

```bash
export PYTHONPATH=.

# MySQL
python3 -m cpqs --db mysql --port 3306 --user root --password '' \
  --rows 10000 --tables 4 \
  --queries 1000000 \
  --queries-per-state 200000 \
  --stale-queries 200 \
  --max-states 8 \
  --overestimate-factor 200 \
  --seed 1

# MariaDB (port 3307)
python3 -m cpqs --db mariadb --port 3307 --user root --password '' \
  --rows 10000 --tables 4 \
  --queries 1000000 --queries-per-state 200000 \
  --stale-queries 200 --max-states 8 --overestimate-factor 200

# CockroachDB
python3 -m cpqs --db cockroach --port 26257 --user root --password '' \
  --rows 10000 --tables 4 \
  --queries 1000000 --queries-per-state 200000 \
  --stale-queries 200 --max-states 8 --overestimate-factor 200

# TiDB
python3 -m cpqs --db tidb --port 4000 --user root --password '' \
  --rows 10000 --tables 4 \
  --queries 1000000 --queries-per-state 200000 \
  --stale-queries 200 --max-states 8 --overestimate-factor 200

# Oracle (password must match ORACLE_PASSWORD; service is usually FREEPDB1)
python3 -m cpqs --db oracle --port 1521 --user system --password oracle \
  --oracle-service FREEPDB1 \
  --rows 10000 --tables 4 \
  --queries 320000 --queries-per-state 40000 \
  --stale-queries 200 --max-states 8 --overestimate-factor 200
```

Timed run (e.g. 10 minutes) with the system `timeout` utility:

```bash
timeout 600 python3 -m cpqs --db mysql --rows 10000 --tables 3 \
  --queries 1000000 --queries-per-state 80000 \
  --stale-queries 300 --max-states 20 --overestimate-factor 200
```

### 6.3 Important CLI flags

| Flag | Meaning | Guidance |
| --- | --- | --- |
| `--db` | Target dialect (required) | `mysql` / `mariadb` / `tidb` / `cockroach` / `oracle` |
| `--host` / `--port` / `--user` / `--password` | Connection | Defaults in §5.3 |
| `--database` | Logical database name | Default `cpqs` |
| `--oracle-service` | Oracle service name | Default `FREEPDB1` |
| `--rows` | Rows in **every** table | Default 10000; do not go lower for real runs unless `--allow-small-rows` |
| `--tables` | Tables per state (2–4) | Default 4 |
| `--queries` | Global executed-query budget | Can be large; wall clock or `--max-states` usually ends the run |
| `--queries-per-state` | Cap per state episode | Works with `--queries` to bound one episode |
| `--stale-queries` | Stall threshold \(K\) | After this many pulls with no larger gap and no new plan → next state |
| `--max-states` | Max database-state rotations | e.g. 8–20 |
| `--overestimate-factor` | Ratio threshold for reporting | Paper-style runs often use **200**; default 8 is more sensitive |
| `--distinct-k` | Distinct values of non-unique `k` | Default 100 |
| `--seed` | RNG seed | Fix for reproducibility |
| `--only-kind` / `--skip-kind` | Include / exclude seed families | Repeatable |
| `--poc-dir` | POC output root | Default `pocs` |
| `--dry-run` | Print SQL without a live DBMS | Generator debugging |
| `--no-analyze` | Skip ANALYZE (usually avoid) | Keep ANALYZE on for real bug hunting |
| `--allow-small-rows` | Allow `--rows < 10000` | Local debugging only |

Notes:

- `--queries` counts **executed** statements only; AST cache hits and failed state mutations do not consume budget.
- When reporting a bug, the tool also checks that `COUNT(*)` does not exceed the access upper bound, to avoid false reports from a wrong bound.

### 6.4 Reading the console

| Prefix | Meaning |
| --- | --- |
| `=== state n/N … ===` | Entered a new database state (profile / row count / …) |
| `ok … expected [L,U] analyzed=…` | Estimate and/or actual stayed inside the allowance |
| `estimate-only …` | Estimate overshot but actual did not → **not** a bug |
| `explain skipped` / `analyze skipped` | Dialect rejected the SQL or ANALYZE was unavailable |
| `suppressed …` | Result cardinality contradicts the bound; report suppressed |
| `BUG #n … -> pocs/...` | POC written |
| `done generated=… bugs=…` | Run summary |

### 6.5 POC files and reproduction

Example path: `pocs/mysql/bug-0001-unique_lookup.sql`. A file typically contains:

- Expected access cardinality and schema profile / path kind
- `CREATE TABLE` / `INSERT` / indexes
- The triggering query
- `EXPLAIN` / `EXPLAIN ANALYZE` excerpts

Replay the statements in order on the matching DBMS. Confirmed cases are also summarized in [`bug.md`](bug.md).

### 6.6 Minimizing POCs (optional)

Shrink unused tables, columns, indexes, and redundant clauses while the estimate + actual overshoot still reproduces:

```bash

python3 -m cpqs.minimize --db mysql --offline   # drop unreferenced objects only
```

## 7. Practical tips and FAQ

1. **Memory:** On an 8 GiB machine, run one container at a time; `docker stop` Oracle immediately after testing.  
2. **Oracle password:** Must match the container `ORACLE_PASSWORD`. If login fails, check `docker logs oracle23` for unfinished initialization.  
3. **TiDB containers:** If an old bind mount is broken, `docker rm -f tidb` and recreate with §5.1; do not reuse a bad mount.  
4. **MariaDB generated columns / leftover MySQL FKs:** Setup disables FK checks and drops `t0`–`t7` before create. If you still see `Table already exists`, manually `SET FOREIGN_KEY_CHECKS=0; DROP TABLE …` and retry.  
5. **False positives:** Do not expect CPQS to invent bounds for hand-written SQL; it only validates queries it generates with certificates. `--overestimate-factor 200` filters small plan noise.  
6. **Dialect gaps:** CockroachDB skips RANGE partitions; CHECK emptiness certificates mainly target Oracle among the five engines in this guide.
